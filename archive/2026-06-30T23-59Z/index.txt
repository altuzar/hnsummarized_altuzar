The setjmp/longjmp problem is that setjmp returns twice: once when called, and again when longjmp is invoked. This creates a torn machine state if the original stack frame has been deallocated. The article walks through concrete examples showing how compiler optimizations (constant folding, register allocation, spill slot reuse) interact dangerously with these APIs. The fundamental challenge is that setjmp saves only registers and stack pointer, not the stack itself. If the function that called setjmp returns or if its thread exits, longjmp will execute on corrupted memory.

Fil-C's solution uses three techniques. First, it makes jmp_buf an opaque pointer to an internal zjmp_buf object that the runtime controls exclusively. Second, it forces setjmp to be called directly (not through function pointers), so the compiler's machinery that treats setjmp specially (disabling spill slot reuse via the returns_twice attribute) always works. Since GPU work per token is small while CPU overhead is fixed, the GPU sits idle waiting for CPU bookkeeping to finish—the "GPU bubble."

Photon's solution overlaps GPU work on token t+1 while CPU commits token t via three mechanisms. First, ping-pong slots: two sets of pre-allocated GPU buffers (input staging, logits output, sampled token, KV cache bookkeeping) prevent collisions when pipelining two steps. The CPU processes one slot's results while the GPU runs the other slot's forward pass on a single compute stream; device-to-host copies run on separate streams. Second, forward-now-sample-later: constrained decoding (which tokens are allowed) depends on previous tokens, but the forward pass doesn't—so launch t+1's forward immediately, then sample after committing t's result to get the correct mask. Third, zombies: when a sequence finishes (hits EOS) at step t but t+1's forward is already queued, mark it finalized but keep processing it as a "zombie" row using refcounting (inflight_refs). Actual teardown happens when in-flight steps finish.
