12:T12f2,Piffer's core thesis: AI's mathematical superiority stems mainly from access to enormous external symbolic workspace (context windows), not from genuinely superior reasoning. He grounds this in cognitive science—working memory, the mental system holding and manipulating information short-term, is severely limited in humans (roughly 5 unfamiliar elements simultaneously). Writing removes this bottleneck; a mathematician uses notation, diagrams, and scratch paper not to communicate but to make reasoning possible.

The article cites empirical evidence that working memory independently predicts math achievement beyond IQ measures. Alloway's longitudinal studies found early working-memory performance predicted later numeracy/literacy even controlling for IQ; meta-analyses confirm working memory contributes distinct variance to mathematical performance across children.

Piffer distinguishes his account from human working memory: an LLM's context window is better understood as "augmented symbolic working memory"—a gigantic external notebook plus imperfect search, not active internal memory. Crucially, LLMs externalize reasoning. When they write "x=6" then later "x+3=9," those statements remain retrievable; humans lose track of such details mentally but must write to preserve them.

Why mathematics specifically? Because it translates uniquely well into explicit symbols. Assumptions, definitions, equations, current objectives, proved results, eliminated cases—almost everything can be written down stably. Unlike informal reasoning (why did Maria stop replying?), where crucial information is hidden and concept meanings are unstable, mathematical symbols are designed to reduce ambiguity. This makes math ideally suited to an intelligence operating via large textual workspace.

Long reasoning chains also matter. A 100-step argument can exceed human ability to coordinate globally even if each step is understandable. AI can preserve nearly everything, enabling much longer chains. Mathematics provides unusually strong feedback (equations check via substitution, code verifies cases, proof assistants validate inference), creating ideal conditions for generation, storage, and verification.

The article predicts AI's advantage should be largest on problems with many interacting constraints, long calculations, extensive case analysis, and exact symbolic bookkeeping—smallest on problems needing one conceptual leap. Trampolines are runtime-generated code stubs placed on the stack when taking the address of a nested function that captures parent scope variables. This requires executable stacks, a significant security vulnerability. Previous workarounds included heap allocation, which adds overhead and creates longjmp-related leaks.

GCC 16 now guarantees that nested functions not accessing parent variables won't generate trampolines, though this was typically ensured under optimization already. Such functions can safely return from their parent scope and the compiler warns when returning capturing functions.

GCC 17 (dev branch) merges Uecker's patch introducing two builtins: __builtin_call_code_address(func) and __builtin_call_static_chain(func). These extract the code pointer and captured context from a nested function, enabling "wide pointers"—structs containing both a code pointer and a data pointer. The __builtin_call_with_static_chain(func(args), data) builtin handles invocation, passing context through the ABI-reserved static chain register. This eliminates trampolines entirely while achieving excellent optimization (the blog shows a three-variable multiplication compiling to a single lea instruction).

The approach doesn't require language changes—users can define generic wide pointer macros wrapping the builtins. Uecker notes this is still GCC-specific and plans future discussion of portable nested function use across clang and GCC, including workarounds for older compilers.

The article begins with a simple question: why are shift amounts 13, 17, and 5 special in Marsaglia's xorshift32 code?

The core insight is that xorshift generators work through consecutive bitwise XOR and shift operations producing deterministic but statistically random sequences. Different shift triplets generate sequences with vastly different periods; only certain "maximal triplets" cycle through all non-zero values (2^32 - 1 for 32-bit generators, 2^64 - 1 for 64-bit). Out of ~30,000 possible triplet combinations for 32-bit, only 162 are maximal.

The article then reframes xorshift mathematically: each operation is a matrix multiplication over GF(2)—the finite field with elements {0, 1} where addition is XOR and multiplication is AND.
