18:T9b3,The vulnerability stems from a cascade of design choices in musl libc. When crypt() fails (e.g., given unsupported algorithm), the Single Unix Specification says it should return NULL. However, musl changed this in 2012 to return "*" instead to prevent crashes in programs that don't check for NULL. That same month, musl added SHA512 crypt with a 256-byte password length cap to prevent DoS; beyond 256 bytes, crypt() fails and returns "*".

OpenSSH, meanwhile, implements timing-attack mitigation for nonexistent users (CVE-2016-6210) by using a real account's salt hash to waste time on failed attempts, even if the user doesn't exist. The collision happens when: (1) the target account has "*" as its password hash (locked accounts like root), (2) sshd grabs another user's salt, (3) the password exceeds 256 bytes, causing musl's crypt() to fail and return "*", and (4) sshd compares "*" == "*" and grants access.

The bug requires all of: musl libc, OpenSSH without PAM, PasswordAuthentication enabled, an account with "*" hash, and another account with a valid password. Alpine AWS/Azure images have these defaults by default (Alpine user with "*" hash and passwordless doas to root). On Debian, Ubuntu, Fedora, glibc systems, or those using PAM, the vulnerability doesn't exist.

The attack requires specific preconditions, most of which are intentional security postures (no passwords set) that only became exploitable through the interaction of multiple independent design decisions.
