The piece, published by Bloomberg engineers on their blog, documents the 9-year journey to standardize proper date/time handling.

The core problem: JavaScript's Date object was hastily ported from Java in 1995 during Brendan Eich's 10-day sprint to create the language. It inherited Java's flaws—mutability, month arithmetic that silently overflows, ambiguous parsing. As JavaScript evolved from simple browser scripts to powering banking systems and trading terminals, Date became a massive pain point. This spawned libraries like Moment.js (created 2011, 100M+ weekly downloads by the 2020s), but those libraries added significant bundle bloat—developers shipped all locale and timezone data without tree-shaking.

Temporal solves this by introducing multiple types: Temporal.ZonedDateTime (immutable, timezone-aware, handles DST correctly), Temporal.Instant (nanosecond precision Unix epoch), and "plain" types (PlainDate, PlainTime, PlainDateTime) representing wall-clock time without timezone complexity. It also brings first-class calendar support beyond Gregorian. The spec is larger than all of ECMA-402 (internationalization), with ~4,500 tests.

Implementation challenges were substantial. Firefox implemented Temporal during spec development (volunteer André Bargull solo-implemented much of it); other browsers lagged. A novel solution emerged: temporal_rs, a shared Rust library that multiple engines (V8, Boa, potentially others) now use. This reduced implementation burden, improved maintainability, and set a rare precedent for cross-engine collaboration.

Temporal is now shipping: Firefox v139, Chrome v144, Edge v144, TypeScript 6.0 beta. Safari has partial support in Technology Preview.

When `ioutil.ReadFile` was deprecated in favor of `os.ReadFile` in Go 1.16, adding `//go:fix inline` to the old function allows `go fix` to automatically replace all calls. More complex scenarios work too: a hypothetical `oldmath.Sub(y, x)` function with swapped parameters can be implemented as `newmath.Sub(x, y)`, and inlining will fix the argument order at all call sites. The feature also works for types and constants via type aliases and const bindings.

At Google, this tool has already prepared over 18,000 changelists to their monorepo, eliminating millions of deprecated function calls. The inliner runs nightly on billions of lines of code, testing and submitting batches of changes automatically.

The implementation is roughly 7000 lines of dense logic because it must handle six major correctness challenges. Parameter elimination attempts to substitute arguments directly when safe, but if a parameter appears multiple times, the tool conservatively introduces explicit variable bindings rather than duplicating magic values. Side effects require hazard analysis to ensure reordering argument evaluation won't change observable behavior—though the inliner must be conservative since it makes permanent source changes and cannot rely on ephemeral optimization details. Constant expression substitution can unexpectedly trigger compile-time checks (e.g., inlining `index("", 0)` would produce the invalid `""[0]`), requiring constraint solving. Shadowing must be checked bidirectionally: caller names in arguments must not be shadowed in the callee, and callee names must refer to the same symbols when spliced into the caller. Unused variables must be tracked to avoid creating new compilation errors. Defer statements prevent true inlining entirely; the tool falls back to wrapping the body in an immediately-invoked function literal `func() { … }()`, but `go fix` policy refuses such literalized calls.

The inliner is conceptually an "optimizing compiler for tidiness"—it must never change program behavior (except for code inspecting the call stack) while producing maximally neat code. Like optimizing compilers, it will never be complete: equivalence checking is undecidable, and human experts will always spot cases where the inliner could be more aggressive.
