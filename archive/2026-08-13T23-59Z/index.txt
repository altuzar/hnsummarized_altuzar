The exploit works by manipulating the DCT (Data Controller) bank-swizzle register at MMIO address 0xf80c2094 with a single xor instruction, causing the memory controller to scramble physical address mappings mid-flight—after all kernel, firmware, and security checks have passed.

The technique exploits the fact that address protections (SMEP, SMAP, IOMMU page tables, access control) operate on physical addresses from the CPU's perspective, but the memory controller performs a final address remapping before reaching actual DRAM. By flipping this remapping, the attacker creates aliases: different physical addresses that reach the same DRAM locations as protected regions (PSP firmware, System Management Mode code, C6 idle-state memory, microcode patches). The trick is performing the swap fast enough (disabling interrupts, priming TLBs, flushing cache) that the system doesn't crash during the scrambled state.

Since the DRAM controller's address transformation is a GF(2) linear map, the author uses the z3 SMT solver to reverse-engineer the unknown scrambling matrices. By placing sentinel values in memory, switching to spaghettified view, finding where they resurface, and collecting pairs of (target, alias) physical addresses, z3 solves for the transformation matrix. This matrix then serves as a "rosetta stone" to compute aliases for any protected address.

The repository includes userspace tools to extract PSP ARM code (showing the fTPM's RSA modexp), dump SMM entry stubs, and resolve firmware carveouts. The write-up is detailed but noticeably AI-generated (acknowledged as Claude), which triggered significant HN commentary.
