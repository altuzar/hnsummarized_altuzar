When query parameters grow too large or complex for URIs—due to encoding overhead, logging concerns, or sheer volume—POST is often misused even though it doesn't signal that the operation is safe and idempotent. QUERY is explicitly both: it accepts a request body like POST but tells caches, proxies, and clients that the operation won't change server state, enabling automatic retries and caching.

The spec positions QUERY as filling a semantic middle ground. GET requires encoding queries in URIs (which get logged and bookmarked); POST doesn't guarantee idempotence. QUERY takes request body content, is safe and idempotent by design, and can optionally return a Location header pointing to an equivalent GET-accessible resource (so future requests can use GET). Servers must declare supported media types via the Accept-Query response header. Caching incorporates the full request body (or a normalized hash of it) into the cache key.

HN comments revealed significant skepticism. Multiple users questioned the practical motivation: long URLs work fine if supported, and complex queries (image inputs, deep JSON filtering) need application-layer caching semantics anyway—baking request-body-as-cache-key into HTTP buys little. Some suggested a simpler POST header like "Vary: request-body" would be backward-compatible. Others noted cache-busting risks if the request body is user-controlled, and that most real-world query caching (embeddings, perceptual hashes) bypasses HTTP layer entirely.

A few appreciated the use case: one commenter said they've been using QUERY for years with Range headers for pagination. Another liked that it removes the awkwardness of treating complex, derived filters as "Resources." A third hoped browsers would add form support (method="query") to avoid POST re-submission warnings. One noted it finally gives EventSource a semantic fit (currently POST is abused for streaming queries).

Naming also drew criticism—"QUERY" conflates with HTTP "query strings" in existing parlance, creating confusion. Several remarked that the RFC reached 5-digit numbers (9999 was the previous ceiling), a minor milestone. Concerns about CORS preflight requirements and the lack of built-in protection against cross-domain misuse were noted. The spec itself was praised as readable for an RFC.
