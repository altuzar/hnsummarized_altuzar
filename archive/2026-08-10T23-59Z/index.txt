If one core misses the timeout window, it remains outside SMM while others execute inside, breaking the security model that assumes exclusive SMM execution.

The attack works by having one thread execute a single instruction so slow it takes ~4 billion cycles—longer than the timeout. The attacker finds a slow MMIO region (in the PoC, 0xfcc68860 on Zen 3 Ryzen) and issues a wide vector load (vmovdqu/ymm/zmm) that stalls for over a second. While this core is stuck, another core triggers SMI. The triggering core enters SMM and waits up to 1 second for the hung core to respond. When the timeout expires, SMM proceeds with the triggering core while the slow core continues executing user-mode code—the sync is broken.

Once desynchronized, an attacker can exploit over 100 known SMM TOCTOU vulnerabilities that check memory values, then use them. Normally these are considered hardware-only (requiring DMA peripherals), but with one core running outside SMM during firmware execution, an attacker can modify shared memory between the firmware's check and use.

The mitigation dilemma is severe: keeping the timeout keeps the bug; removing it hangs systems when a core legitimately stalls; increasing it tanks performance on many-core systems forced to synchronize repeatedly.
