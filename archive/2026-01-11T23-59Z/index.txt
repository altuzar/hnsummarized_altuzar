This creates several cascading problems.

First, consistency: Elasticsearch can only guarantee atomicity at the single-document level. Multi-document writes succeed independently and potentially out-of-order. Reads are split into two modes—GET by ID returns the latest version, but SEARCH only looks at asynchronously-refreshed Lucene segments, so recent writes may not be visible. Databases handle this with transactions and isolation levels; Elasticsearch has neither.

Second, schema evolution: index mappings are immutable in Elasticsearch. Changing a field type requires creating a new index and reindexing all documents. When Elasticsearch is downstream of another database this is just a painful network transfer; when it's the only store, it's a high-risk operation under load with no safety net.

Third, querying limitations: Elasticsearch's Query DSL handles search and aggregations well but lacks relational features. Joins are missing or partial. The article shows an example of a straightforward SQL query with joins and GROUP BY—routine in Postgres but requires denormalization, children, or application-layer stitching in Elasticsearch. Elastic's newer ES|QL and SQL features exist but are still bound by Lucene's index model and introduce query syntax confusion (Query DSL, ES|QL, SQL, EQL, KQL).
