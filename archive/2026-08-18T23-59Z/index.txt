When games request more VRAM than physically exists, data must be evicted to CPU RAM—historically causing severe performance drops or crashes.

The author explains the technical reality: PCIe 4.0x16 provides ~32GB/s bandwidth, meaning only ~1GB of GPU-to-CPU memory can be accessed per frame at 30fps. However, not all memory is equally impacted by eviction. With good cache hit rates, accessing CPU-backed memory can remain acceptable. The real problems emerge from stability issues during command submission.

The core technical issue: when the kernel tries to evict allocations to make room for new submissions, concurrent submissions can deadlock if each holds locks the other needs. Previously, amdgpu would simply fail with -EDEADLCK instead of retrying. The TTM memory management layer wasn't using the drm_exec locking helper that implements proper wound-abort-retry semantics. The author fixed this by rebasing 2024 patchsets and debugging week-long hangs from remaining bugs.

After fixing crashes, performance was terrible due to "ping-pong" eviction: the kernel would constantly evict and re-evict the same buffers as competing processes took turns. Display scanout buffers caused the worst pathology—their requirement for physical memory contiguity meant evicting multiple GiB of unrelated data just to make room for ~32MB of framebuffers.

Solutions implemented: (1) Heuristics throttling aggressive eviction—"hard throttle" for milliseconds, then "soft throttle" for seconds before relaxing restrictions. (2) Integrating Vulkan's vkSetDeviceMemoryPriorityEXT to let applications hint which allocations are eviction-friendly, reordering the LRU list accordingly.

Real-world results: Indiana Jones with 1GB overcommitted (9/8GB) achieves 19.6ms frametimes (playable), even at 2GB overcommitted (10/8GB) reaches ~29.8ms though with variance.

Git's distributed design maps poorly to centralized hosting: packfiles are large binary files requiring sequential disk access following a DAG (directed acyclic graph) structure where every node lookup needs the previous node's output. Distributed hash tables fail because object retrieval becomes prohibitively expensive with round-trip latency per lookup. GitHub tried filesystem distribution (NFS, GFS, DRBD) but these don't work because Git makes assumptions about local filesystem semantics—locking, tearing, sync behavior—that break over networks.

GitHub's actual solution, "Spokes" (circa 2013), stores full repositories on NVMe, replicates to multiple machines, and keeps replicas strictly consistent using three-phase commit (3PC). This required careful choreography: fan out packfiles in parallel, then 3PC the reference transaction. Works well but has two fatal flaws for 2026 workloads: (1) 3PC's latency is bounded by the slowest replica, so adding replicas for large monorepos tanks push throughput; (2) treating repositories as "pets" requires routing tables, checksumming, corruption detection—high operational burden.
