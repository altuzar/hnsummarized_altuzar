Once serde is ubiquitous, creating a better alternative (nextserde) is pointless because every downstream crate would need to implement support for both. Users wanting the alternative must fork and patch every dependency. This isn't a flaw in any library but a consequence of the language's coherence and orphan rules.

The post explains why coherence exists. Coherence prevents the "HashMap Problem": different crates implementing Hash differently for the same type, then passing HashSets between them with inconsistent lookup behavior. Coherence also protects soundness—without it, different crates could assign different types to associated types (one sees `*const u8`, another sees `Box<u8>`), enabling unsafe transmutation in safe code. The orphan rules (preventing impl of external traits for external types) exist to (1) ensure composability—if crates b and c both implement the same trait for the same type, crate d can't use both, and (2) support dynamic linking without link-time coherence checking.

The post surveys existing proposals: Binary Crate Exemption (only binaries skip orphan rules—doesn't help libraries), Deferred Coherence (check only at link time—breaks composition and dynamic linking), Coherence Domains (workspaces as units—still breaks across dependency versions), Fundamental attribute (subtle, doesn't solve evolution), Syntactical Equality (unsound with dynamic linking), Marker Traits (sound but limited), Specialization (helps some cases, not evolution), and Reflection/Comptime (promising but feels like dodging the core issue).

The core proposal: introduce named impls (`impl MyImpl = Clone for Type { ... }`) and explicit trait-bound parameters so callers specify which impl to use (`function::<T + MyImpl>()`). With incoherent traits, multiple impls can coexist; the compiler doesn't auto-select. This desugars the trait system into "impl-passing" akin to dictionary-passing style. Soundness is preserved because impl selection is explicit in types—`HashMap<K: Hash>` bounds Hash at the struct level, so the hash function is part of the type, preventing the HashMap problem. Associated types similarly carry their impl as part of the type, preventing the transmutation soundness hole.
