He notes that three issues from his 2015 post have since been fixed or nearly fixed, but larger systemic problems remain.

High-level issues center on project health. Review capacity is insufficient—thousands of contributors but far fewer qualified reviewers means PRs stall and get rubber-stamped by unqualified approvers. The PR author-driven assignment model is especially bad for newcomers unaware of whom to request. C++ and IR API churn is simultaneously strength (addresses past mistakes) and weakness (forces constant downstream updates), enforced by "upstream or GTFO" philosophy where out-of-tree code doesn't influence decisions. Build time is severe for low-spec hardware; 9 million LOC monorepo with C++ compilation overhead, debug info, and linking create gotchas even with workarounds. CI consists of 200+ post-commit buildbots running multi-hour tests, never fully green, diluting signal on real failures; pre-merge testing helped but doesn't solve buildbot flakiness. End-to-end testing is weak—unit tests for passes are thorough, but phase-ordering and backend pipeline tests are scarce, and the separate llvm-test-suite lacks comprehensive coverage for basic operations across float formats, integer sizes, vectors. Backends diverge: implementations are heterogeneous, target hooks multiply to avoid dealing with fallout on other targets, creating duplication.

Compilation time remains problematic despite recent tracking improvements. -O0 is particularly bad; the TPDE alternative shows 10x improvements possible. Performance tracking infrastructure is conspicuously absent despite public concern—LNT exists but is broken, has poor UX, minimal submissions, and can't be triggered by PRs.

IR design issues are technical but structural. Undef values for uninitialized memory have multi-use problems (different values at each use, preventing optimizations) and are hard to reason about; replacement by poison requires new IR features like byte type. Remaining miscompilations often combine theoretical-only manifestations with deep IR design issues; some require simple-but-approximate or very complex-but-correct choices. The formal specification working group is addressing these. Constraint encoding has proliferated across poison flags, metadata, attributes, assumes—metadata is lost too often, assumes retained too often. Floating-point semantics are fragmented: signaling NaNs and exceptions use parallel constrained FP intrinsics, denormal handling is target-specific (scalar vs vector), x87 excess precision is unmodeled.

Partial migrations span years with coexisting implementations. The new pass manager was introduced over a decade ago, used by default for middle-end five years ago, but the backend still uses legacy PM. GlobalISel, introduced a decade ago to replace SelectionDAG, remains non-default everywhere; AMDGPU and AArch64 have partial support but can't yet default to it because new SDAG optimizations keep breaking parity.

ABI/calling convention handling is split between frontend and backend with zero documentation of the contract; proper FFI requires copying Clang's undocumented approach. Target features and ABIs are wrongly entangled—enabling more target features can change the calling ABI by enabling different registers, making calls between different-feature functions incompatible. Newer architectures handle this properly but older ones don't. Related is builtins/libcalls fragmentation: two sources of truth (TargetLibraryInfo for middle-end, RuntimeLibcalls for backend) based on target triple; changing --rtlib=compiler-rt isn't tracked, blocking use of compiler-rt-only functions or custom runtime libraries.

Context/module dichotomy: types and constants live in context (per-thread), modules hold functions/globals and data layout. Types can't reliably determine size without threading data layout everywhere, splitting subsystems. The split provides modest convenience for module linking but adds friction throughout. LICM treats code motion as canonicalization, always hoisting instructions without register pressure modeling. Sinking back into loops rarely happens except through rematerialization or addressing-mode specialization, leaving unnecessary spills.
