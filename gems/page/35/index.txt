19:T611,Jake Lazaroff's interactive tutorial explains state-based CRDTs—data structures that sync across peers without a central authority. A CRDT requires a value (application state), metadata state, and a merge function satisfying three properties: commutativity (order-independent), associativity (grouping-independent), and idempotence (self-merging is harmless).

The article covers Last-Write-Wins (LWW) Registers, which resolve conflicts by timestamp and peer ID, and LWW Maps built by composing registers. Key insight: deletions use "tombstones" (null values) rather than removal, preserving metadata to distinguish deletions from missing keys. This makes CRDTs monotonically increasing—they can only add information, not truly remove it. The article promises a follow-up on building a collaborative pixel art editor.

Comment threads note important limitations. Last-Write-Wins CRDTs discard data during conflicts; more nuanced structures exist. Commenters highlight operation-based CRDTs (transmitting operations, not full state) for scenarios like append-only logs and counters, which converge non-destructively. One developer cautions against CRDTs generally, noting central servers handle permissions, locks, and conflict resolution better for typical use cases. Another counters that ordered, latency-sensitive operations (like concurrent AI agent state updates) benefit from hybrid approaches combining operational transformation with CRDT semantics.
