13:Tc06,Z80-μLM is a fully functional language model that runs on 4MHz 1970s hardware with 64KB RAM. The entire system (inference, weights, chat UI) compresses into a 40KB .COM file. It uses extreme quantization: 2-bit weights (values of -2, -1, 0, +1), 128 trigram hash buckets for input encoding (typo-tolerant but word-order invariant), and pure 16-bit integer arithmetic on Z80 register pairs.

The key technical achievement is quantization-aware training (QAT). Rather than post-hoc compression, the model learns under constraint: both float and integer-quantized forward passes run in parallel during training, with loss computed on how well knowledge survives the 2-bit grid. Weights are pushed toward {-2,-1,0,+1} using straight-through estimators, with overflow penalties matching the Z80's 16-bit accumulator. By convergence, the model has already adapted to real hardware limitations.

The architecture is a simple MLP: 128 query trigram buckets + 128 context buckets as input, configurable hidden layers (e.g., 256→192→128), output neurons per character. No attention, no RNN—just matrix multiplies. Character-by-character autoregressive generation. The core Z80 loop unpacks 2-bit weights from packed bytes, multiply-accumulates with activations, and shifts right by 2 bits per layer to prevent overflow.

Two examples ship pre-built: tinychat (casual Q&A with personality), and guess (20 Questions game where the model knows a secret). The author trained on data from Claude API (generating 20 Questions examples), which he joked might violate ToS but notes permissive alternatives exist.

Comments reveal strong appreciation for the constraint-solving and retro appeal. One commenter built a VT100+Z80 emulator bridge in Unreal Engine and this fits perfectly. Another noted the project proves concepts that could have existed in the 1960s, changing science fiction. A Fortran IV neural network on 1960s punched cards was mentioned as spiritual kin.

Crucial pushback: Some note the actual intelligence is minimal—the model succeeds because humans project meaning onto sparse outputs. 27:Tc0f,The article walks through what a camera sensor truly captures: raw 14-bit analog-to-digital converter (ADC) values mapped to 0-255, which look like a nearly featureless gray image of a Christmas tree. The first lesson is histogram stretching—the ADC actually only uses a narrow range (2110-13600), so the author rescales to white and black points to reveal contrast.

Next comes the Bayer matrix revelation. Camera sensors can't see color; they measure total brightness. A color camera uses a grid of red, green, and blue filters, with green at 50% (RGGB pattern). This is justified not just for color balance but because the human eye is most sensitive to green—it carries the luminance (detail) channel while red/blue act as "color difference" layers. Demosaicing (averaging with neighbors) reconstructs full RGB at each pixel.

The dynamic range problem comes next. Monitors and eyes have limited dynamic range, and human perception of brightness is nonlinear. If you display linear sensor data directly, midtones appear far darker than they should. Gamma correction and tone curves fix this, but applying curves to each channel caused a green cast (worsened by the 2:1 green filter ratio). White balance (scaling each color channel by a constant) corrects this, but must be done in linear space before re-applying gamma.

The final result required: black point correction, gamma curves, white balance, and desaturation of highlights (a film-like effect). The "in-camera JPEG" is massively processed—not "fake," just a different rendering of the same data. The author emphasizes that replicating human perception within display constraints is hard; there's no shame in adjusting photos.

Comments add crucial context: The 50% green pattern isn't just about color but spatial resolution—demosaicing algorithms reconstruct green first to build a high-res luminance map, then interpolate red/blue. The port required reverse-engineering and creative driver work. Windows 1 for the Apricot survived in the wild, but only in "fast boot" form where drivers were linked into the kernel binary, making them inaccessible.
