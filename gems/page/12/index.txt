12:Te8e,Dominic Szablewski published Xibalba 64, a new N64 FPS released physically through ModRetro's M64 hardware clone. This is only the second new N64 game published commercially since the console's commercial life ended (Xeno Crisis came in 2023). The project came about after Szablewski ported his 2010 JavaScript Impact game engine to C, creating high_impact with modular platform and rendering backends.

For the N64, Szablewski built a libdragon platform backend, leveraging the open-source library as "SDL for the N64." The N64 hardware presented challenges: a 93 MHz MIPS processor with the Reality Coprocessor (RDP and RSP coprocessors). The RSP is a programmable vector processor requiring custom microcode, while the RDP is fixed-function and notoriously quirky. Official Nintendo libultra is legally risky, making libdragon essential.

The game expanded from Szablewski's original 2014 WebGL demo with more levels, enemies, and weapons. Though built on a 2D engine, it works as a 3D FPS (no elevation) through clever vec3_t union definitions allowing free conversion to vec2_t for physics. He optimized rendering by replacing the portal system with raycasting: 320 rays scan the field of view, with recursive subdivision and skybox detection. Tiny3D, another open-source library, handles 3D graphics with RSP microcode.

The N64's 4 KB texture memory bottleneck required extreme care: Szablewski batched draw calls into 64-bit structures, sorted them per frame, and arranged tile sheets as single columns to minimize texture uploads. 4-bit indexed colors maximized pixel density. The result: stable 60 FPS. Four-player split-screen drops below 60 occasionally but remains fluid.

Audio consumed ~31 MB of the 32 MB ROM. Modern Opus codec was too expensive; libdragon uses 4-bit VADPCM, decoded on the RSP. Szablewski's friend Andreas Lösch composed the soundtrack. The cartridge uses a map compiler converting JSON level files to binary structs with big-endian encoding for N64, avoiding expensive runtime JSON parsing (~100 ms saved).

Development environment included libdragon's comprehensive toolchain, the Ares emulator (now with accurate RDP/RSP emulation including RSP timing), and a SummerCart64 flash cartridge with USB-C for rapid iteration. Szablewski used an HDMI capture card to monitor real hardware on his PC. The level editor is a single self-contained HTML file that auto-generates from C source.

Publishing went smoothly: an email to ModRetro's customer service reached the publishing head within a day. The contract was straightforward; Szablewski negotiated permission to open-source the engine later. ModRetro provided a late-stage pre-production M64 (no changes needed), help with box art, and manual layout. Sales look promising early, though Szablewski notes this won't sustain full-time work but covers "a few nice holidays."

37:T9f4,The article presents a practical optimization for A* pathfinding using landmark-based heuristics. Standard A* relies on distance-based heuristics (Manhattan, Euclidean) that don't account for map structure and often point searchers in wrong directions. The technique precomputes shortest paths from every node to a small set of "landmark" nodes (e.g., 4–8 points), then uses the triangle inequality to derive tighter lower bounds: cost(B,X) ≥ cost(B,L) - cost(X,L). At query time, the heuristic function takes the maximum across all landmarks, improving guidance without modifying A* itself.

Key insight: a single landmark only helps if it's "past" the goal—that is, if the start-goal path passes through or near a line from goal to landmark. Multiple strategically-placed landmarks cover different directions and path types. Placement is application-specific: high-traffic areas like dining halls in Dwarf Fortress deserve landmarks, while random-path analysis can find placements automatically if map structure isn't known in advance.

The author spent 11 years understanding this technique sufficiently to explain it clearly. Implementation requires running Dijkstra from each landmark once and storing an (nodes × landmarks) cost table, then modifying only the heuristic function. Demos show 40–80% reductions in explored nodes on real game maps. The approach combines well with other optimizations.
